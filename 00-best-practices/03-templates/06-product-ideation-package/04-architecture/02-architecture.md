### Component Descriptions

**Application Layer**
The user-facing layer. Server components handle the dashboard and list views (read-heavy, no client state needed). Client components handle the editor and interactive views (real-time, interactive). All data fetching goes through Route Handlers — no direct database access from components.

**Route Handlers (API)**
The internal API. Handles CRUD operations for core entities. Validates input, enforces authorization, and delegates to background workers for async operations. Returns JSON. Not a public API — only consumed by the frontend.

## Data Architecture Philosophy

<!--
Explain the design decisions that govern how data is structured and accessed.
This is not a list of schema details (those are in 10-data-model.md).
This is about the philosophy: why these choices were made, and what they protect against.
-->

**Relational over document store**: The data has clear relationships that benefit from referential integrity. A relational schema prevents orphaned records and allows reliable joins.

**AI output is stored, not re-generated**: Every AI-generated artifact is persisted on creation. The system never re-generates on read. This ensures reproducibility, enables human review, and controls LLM API costs.

**Human edits are preserved separately from AI output**: [Describe the pattern — override fields, separate records, or equivalent.] The original AI output is never overwritten.

**Conversation history is append-only**: [If applicable — conversation/chat messages] are never deleted or edited. The full history is the source of truth.

**Job state in the database**: Background job state is stored in the primary database on the relevant entity (e.g., `Document.status`), not in a separate job queue table. This simplifies the operational model at MVP scale.

  description: Update status or editable fields
  caller: Detail view (client)

    status: [StatusType] | undefined
  response:
    item: [PrimaryEntity]

# [Output Resource]

POST /api/[primary-resource]/:id/[output]:
  description: Create a new output for an item
  caller: Detail view (client)

  description: Fetch an output with all sections and messages

### Scaling Considerations (Phase 2+)

- If processing volume grows, move background workers to a dedicated scheduled service.
- If LLM call volume creates rate limit pressure, introduce a request queue with retry/backoff.
- If multiple users collaborate simultaneously, introduce WebSocket or server-sent events for the editor (currently assumes single-user per session).
