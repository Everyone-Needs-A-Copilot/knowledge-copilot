# End-to-End Journey Mapping

<!--
FACTORY AGENTS: SD (Service Designer) + UXD (UX Designer)
==========================================================
This document is NOT facilitated. It is generated by the SD and UXD agents
working from the completed experience documentation.

The SD owns the journey mapping and the handoff logic — what flows between
stages and between systems. The UXD maps each journey stage to the specific
screens that carry it and identifies where Moments That Matter occur in the
navigation flow.

INPUTS (read all before writing):
- 02-user-guides/02-service-design/02-journey-maps.md
    The primary source. Contains: persona definitions, stage-by-stage journeys,
    emotional arc, touchpoints, struggling moments, and intelligence handoffs.
    Every persona journey in that document must appear here as a screen-mapped flow.
    Stage names used in that document are fixed — do not rename them here.
- 02-user-guides/20-service-design/30-jtbd.md
    Jobs to Be Done by persona and priority. Each screen in the E2E flow must be
    mappable to at least one Job. If a screen cannot be mapped to a Job, flag it
    as a candidate for removal.
- 02-user-guides/20-service-design/40-moments-that-matter.md
    Critical inflection points where the product earns or loses trust.
    Each MTM must be placed on a specific screen in the "Moments That Matter
    Screen Mapping" section. Use the MTM IDs (MTM-1, MTM-2, etc.) from that doc.
- 03-developer-guides/04-e2e-mapping/01-view-map.md
    The view inventory. Use screen names from the view map — do not invent
    screen names that do not exist in the inventory. If a new screen is needed,
    add it to the view map first, then reference it here.
- 04-architecture/20-architecture.md
    Defines the ecosystem boundary: "What Flows In", "What Flows Out", and
    "External Services Called." Use this section to populate Ecosystem Handoffs.

GATE: G6 — E2E Mapping Complete
This document must be complete before G6 is passed. Complete means:
- Every persona from the journey maps has a screen-mapped journey in this document
- Every MTM is placed on a specific screen with a design implication
- All ecosystem handoffs from the architecture doc are reflected here
- All internal handoffs between views are documented
- Acceptance criteria are written for each journey stage in Given/When/Then format

PROCESS:
1. Read 02-journey-maps.md. List every persona and every journey stage.
   Extract struggling moments and the emotional arc.
2. For each stage, identify which screen(s) from the view inventory carry that
   stage. One stage may span multiple screens; one screen may carry multiple stages.
3. For each Moment That Matter (from 40-moments-that-matter.md), identify the
   exact screen where it occurs. Record both the success state and failure state
   on that screen.
4. Extract all ecosystem handoffs from the architecture doc and document the
   failure mode for each.
5. Map internal handoffs — state transitions between views that carry critical
   data. These are the most common source of journey failures.
6. Write acceptance criteria per stage in Given/When/Then format. Criteria must
   be verifiable by QA without subjective interpretation.

STYLE:
- Stage names must match 02-journey-maps.md exactly.
- Screen names must match 01-view-map.md exactly.
- Every acceptance criterion must have a concrete observable result —
  no "should work correctly" or "should feel responsive."
- Write from the user's perspective — what they experience — not from the
  system's perspective.
-->
