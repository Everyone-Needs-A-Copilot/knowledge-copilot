## Test Strategy Overview

The test strategy is organised into five layers. Each layer targets a different failure mode.

| Layer | Type | What It Tests | Typical Tooling |
|-------|------|--------------|-----------------|
| Unit | Fast, isolated | Business logic: core calculations, data transformations, input validation | [Fill from architecture — Jest or Vitest] |
| Integration | DB + API | API endpoints against a real test database; background worker pipelines; external service stubs | [Fill from architecture — supertest, pg-test or equivalent] |
| E2E Smoke | Full browser | Complete user journeys through the deployed application with fixture data | [Fill from architecture — Playwright] |
| Performance | Load + latency | Core workflow latency, page load under concurrent sessions | [Fill from acceptance criteria — k6 or Lighthouse] |
| Accessibility | WCAG compliance | All user-facing views, interactive elements, and dynamic content at WCAG 2.1 AA | [axe-core via Playwright or jest-axe for components] |

Security testing is documented in `02-security.md`. This document references which security checks run in the standard QA cycle.

### Coverage Targets by Layer

| Layer | Target | Rationale |
|-------|--------|-----------|
| Unit — core business logic | 100% branch coverage | Core logic errors corrupt user trust and lead to bad decisions |
| Integration — API happy paths | 100% of endpoints in API contracts | Every documented endpoint must be verified before release |
| Integration — error handling | Top 3 error modes per endpoint | Unhandled errors are the leading cause of user-facing failures |
| E2E Smoke — primary journey | 100% of happy path stages | The happy path must always work; a broken smoke test blocks release |
| Accessibility — critical views | 100% automated; 80% manual test coverage | Critical views are presented to stakeholders; inaccessible screens are unacceptable |

## Security Testing

The full security test plan is in `02-security.md`. The following security tests run as part of the standard QA cycle (every CI run or every deployment):

| Check | Frequency | Tooling | Blocking? |
|-------|-----------|---------|----------|
| Secret detection | Every commit (pre-commit hook) | git-secrets or truffleHog | Yes — commit is rejected |
| Dependency vulnerability scan | Every CI run | npm audit / Snyk | Yes — critical and high CVEs block merge |
| SAST | Every CI run | ESLint security rules; CodeQL | Yes — critical findings block merge |
| OWASP ZAP baseline scan | Every deployment to staging | OWASP ZAP (automated mode) | Yes — new high-severity findings block promotion |
| Auth enforcement | Every E2E smoke test run | Playwright — verify protected routes redirect unauthenticated users | Yes |
| Input validation (XSS) | Per release | Manual test + Playwright assertions on text inputs | Yes |

Tests requiring an independent security audit (Tier 1 surfaces per `08-design-factory/RISK-CLASSIFICATION.md`) are outside this test plan and are managed in `02-security.md`.

## Accessibility Testing (WCAG 2.1 AA)

WCAG 2.1 AA applies to all user-facing views without exception.

### Automated Testing (Every CI Run)

- `jest-axe` or `axe-playwright` runs against all views in the E2E smoke test suite
- Zero WCAG 2.1 AA violations is the pass condition
- Violations are blocking — they fail the build
- Suppressed violations require documented justification and product owner approval

### Manual Testing (Per Release)

Manual testing covers areas automated tools cannot reliably detect:

| Check | Scope | Method |
|-------|-------|--------|
| Keyboard navigation | All interactive elements on all critical views are reachable and operable by keyboard alone | Manual tab traversal |
| Focus indicator visibility | All focused elements have a visible focus ring; no focus ring is clipped by overflow | Manual inspection at 1280px |
| Screen reader announcements | Dynamic content (AI outputs, status changes) is announced correctly when it appears | NVDA on Windows; VoiceOver on macOS |
| Color contrast | All text meets 4.5:1 contrast ratio; UI components meet 3:1 | Colour Contrast Analyser |
| 200% zoom | All critical views are functional and readable at 200% browser zoom | Manual |

## Cross-Model Review Process

If the product uses AI-generated outputs, those outputs require a distinct QA approach. A standard assertion cannot determine whether AI output is accurate or acceptable — it can only determine whether output was produced.

### AI Output Review

An AI output test fixture pairs a defined input with a pre-approved acceptable output range and minimum quality requirements.

| Fixture ID | Input description | Acceptable output range | Quality requirement | Approved by |
|-----------|------------------|----------------------|----------------------|------------|
| AI-FIXTURE-01 | [Representative input] | [Acceptable range] | [Minimum quality bar] | [Product owner sign-off required] |

Note: Fixtures must be approved by the product owner before being committed. They represent a business judgment about what constitutes acceptable AI output and will need periodic re-review as the model changes.

## Risk-Based Rigor

Test effort is proportional to the consequence of failure, not to feature size.

| Area | Risk Level | Why | Required rigor |
|------|-----------|-----|---------------|
| Core business logic | Critical | Incorrect outputs lead to bad decisions; the product's core intelligence | 100% branch coverage; integration tests for all edge cases; matches Tier 2 minimum in `RISK-CLASSIFICATION.md` |
| Authentication and session management | Critical | Unauthorized access exposes sensitive data | Matches Tier 1 in `RISK-CLASSIFICATION.md`; independent audit lane required |
| Data processing pipeline | High | A processing failure silently blocks downstream features; hard to detect without monitoring | Integration tests for all supported formats; explicit error state tests; alert verification |
| Export / output generation | High | A corrupt output file destroys work with no recovery | Integration tests with content assertions; manual review of output formatting |
| API input validation | High | Injection or malformed input has cascading effects | Boundary tests for all API endpoints; schema validation unit tests |
| Core UI filtering and sorting | Medium | Filtering bugs are visible but do not cause data loss | E2E tests for each filter type; unit tests for filter logic |
| Settings configuration | Medium | Misconfigured settings affect future operations, not current ones | Integration tests for happy path; manual smoke test per release |
| Empty states and error states | Low | Cosmetic failures; no data loss | Presence assertions in E2E smoke tests; no dedicated test effort beyond smoke coverage |
