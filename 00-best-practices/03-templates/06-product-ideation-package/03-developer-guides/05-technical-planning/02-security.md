## Authentication & Authorization

### Authentication Requirements

| Requirement | Specification |
|-------------|--------------|
| Authentication method | [Fill from technical planning. Record the choice and rationale in the ADR.] |
| Password policy | Minimum 12 characters; no arbitrary maximum; hashed with bcrypt at cost factor >= 12; common password list rejection |
| Multi-factor authentication | Required for all users with `admin` role; available (not required) for other roles |
| Failed login handling | Account locked for 15 minutes after 5 consecutive failures; failure event logged with IP and timestamp |
| Session token type | Opaque server-side session token; not a client-readable JWT containing sensitive role or identity claims |
| Credential transmission | Credentials transmitted only over HTTPS; never in URL parameters or log output |

### Authorization Model

{{PRODUCT_NAME}} uses role-based access control (RBAC) based on `User.role`.

| Role | Permitted actions | Explicitly denied |
|------|------------------|------------------|
| `admin` | Full system access; user management; system configuration | Cannot assign `admin` role to others via the UI (requires direct database action + second admin approval) |
| `[primary role]` | [Primary actions] | [What they cannot do] |
| `reviewer` | Read-only access; record approval | Cannot edit content; cannot override evaluations |

### Authorization Implementation Rules

- Every API route handler must enforce authorization before reading or writing data — no route is publicly accessible without explicit authentication verification
- No client-side role — role is always read from the server-side session; client-side role display is informational only
- No role can access raw external API credentials — these are server-side environment variables only
- Role escalation (changing a user's role) requires `admin` privileges and is logged

## Session Management

| Requirement | Specification |
|-------------|--------------|
| Idle timeout | 2 hours of inactivity |
| Absolute session maximum | 12 hours regardless of activity |
| Session storage | Server-side session store; session ID stored in an `HttpOnly`, `Secure`, `SameSite=Strict` cookie |
| Logout behaviour | Session is invalidated server-side immediately on logout — cookie deletion alone is not sufficient |
| Concurrent sessions | Maximum 3 concurrent sessions per user; the oldest session is invalidated when the limit is exceeded |
| Session fixation prevention | A new session token is issued after every successful authentication — the pre-authentication session token is invalidated |
| Secure flag | All session cookies must carry the `Secure` flag; no session cookies over HTTP |

## API Security

### Input Validation

All inputs at the API boundary must be validated before any processing.

| Input type | Validation requirement |
|-----------|------------------------|
| Path parameters (IDs) | Must be a valid UUID (RFC 4122); reject non-UUID format with HTTP 400 |
| Query parameters | Type-checked; numeric bounds enforced; unknown parameters rejected with HTTP 400 |
| Request bodies | Schema-validated against the documented TypeScript interface; unknown fields rejected; empty required fields rejected |
| File retrieval | MIME type and file extension must match; maximum file size enforced; files are not executed |
| Free-text user input | Maximum character length enforced; content is not interpolated into system commands; prompt injection mitigations applied |

### API Key Management

| Key | Storage | Access | Rotation policy |
|-----|---------|--------|-----------------|
| External AI API key | Environment variable only; never in source code, config files, or database | Server-side only; never sent to the browser | Rotate on any suspected compromise; access audited quarterly |
| Database credentials | Environment variable only | Server-side only | Rotate on team membership change; minimum annually |
| File storage credentials | Environment variable only | Server-side only | Rotate on suspected compromise; minimum annually |

`.env` files are `.gitignore`d without exception. `.env.example` documents all required variable names with placeholder values only — never with real credentials.

### CORS Policy

{{PRODUCT_NAME}} does not expose a public API. CORS is restricted to the application's own origin. Requests from other origins are rejected with HTTP 403.

### Rate Limiting

| Endpoint or endpoint group | Limit | Window | Action on exceed |
|---------------------------|-------|--------|-----------------|
| AI-assisted endpoints (chat, generation) | 20 requests | Per minute per authenticated user | HTTP 429; `Retry-After` header included |
| All authentication endpoints | 5 attempts | Per 15 minutes per originating IP | Temporary IP block; alert generated |
| All other authenticated endpoints | 200 requests | Per minute per authenticated user | HTTP 429 |
| Unauthenticated requests to protected routes | 0 allowed | — | HTTP 401 immediately; any pattern of probing is logged |

## Data Protection

### Encryption at Rest

| Data | Encryption requirement |
|------|----------------------|
| Primary database | Disk-level encryption via the managed DB provider's encryption-at-rest feature (AES-256 minimum) |
| File storage | Server-side encryption on the S3-compatible bucket (AES-256) |
| Application secrets and environment variables | Stored in the infrastructure's secrets management service; never in plaintext on disk or in source control |
| Exported files | Not encrypted at rest after download — the downloaded file is the user's responsibility; files are deleted from server storage after 30 days |

### Encryption in Transit

| Channel | Requirement |
|---------|-------------|
| Browser ↔ Application | TLS 1.2 minimum; TLS 1.3 preferred; all HTTP redirected to HTTPS |
| Application ↔ Database | TLS-encrypted connection string required; plaintext database connections are not permitted |
| Application ↔ External API | HTTPS |
| Application ↔ File storage | HTTPS |

HSTS must be enabled on the application domain: `Strict-Transport-Security: max-age=31536000; includeSubDomains`.

### PII Handling

| PII type | Where stored | Protection |
|----------|-------------|-----------|
| User email | `User.email` | Stored hashed for inactive accounts; displayed only to the user and admins |
| User name | `User.name` | Displayed within the application; not exposed in exports |

**Deletion policy:** On account deletion request, `User.email` is replaced with a SHA-256 hash. `User.name` is replaced with "Deleted User." Records created by the user are retained for audit purposes but disassociated from the email.

### Backup and Retention Policy

| Asset | Retention | Backup frequency | Recovery test |
|-------|-----------|-----------------|---------------|
| Primary database | Daily backups; 30-day retention; point-in-time recovery | Automated daily | Restore test quarterly |
| File storage | Versioning enabled; deleted files recoverable for 30 days | Versioning (continuous) | Recovery test quarterly |
| Exported files | Deleted from server storage after 30 days | Not backed up — user's downloaded copy is authoritative | — |

## OWASP Top 10 Coverage

| OWASP ID | Category | Applies? | Mitigation |
|----------|---------|---------|-----------|
| A01 | Broken Access Control | Yes | RBAC enforced on every API route handler before any data read or write; resource ownership validated before access; E2E smoke tests verify auth enforcement on all protected routes |
| A02 | Cryptographic Failures | Yes | TLS everywhere; AES-256 at rest; `HttpOnly` and `Secure` cookies; sensitive data never logged or included in URLs; HSTS enabled |
| A03 | Injection | Yes | Parameterized queries only (no raw SQL string concatenation); ORM enforces this; user inputs are sanitized and length-bounded; file content is extracted as text only — never executed |
| A04 | Insecure Design | Yes | Threat model documented before implementation; RBAC designed before code; security review included at G8 gate; independent audit required at launch |
| A05 | Security Misconfiguration | Yes | `.env.example` with placeholder values only; CORS locked to own origin; no default credentials left enabled; security response headers applied to all responses |
| A06 | Vulnerable and Outdated Components | Yes | `npm audit` on every CI run; Snyk monitoring for new CVEs; dependencies pinned to minor versions |
| A07 | Identification and Authentication Failures | Yes | Account lockout after 5 failures; `HttpOnly` / `Secure` / `SameSite=Strict` cookies; session invalidation on logout (server-side); session fixation prevention; MFA required for `admin` role |
| A08 | Software and Data Integrity Failures | Yes | CI pipeline enforces integrity checks; dependency lockfile committed and verified |
| A09 | Security Logging and Monitoring Failures | Yes | All authentication events logged with timestamp and IP; all API 4xx and 5xx responses logged; logs shipped to a centralized store |
| A10 | Server-Side Request Forgery (SSRF) | Yes | External URLs are validated against an allowlist before use; user-supplied content is never directly used as a fetch target without allowlist validation |

### Required Security Response Headers

All responses from the application must include:

```
Strict-Transport-Security: max-age=31536000; includeSubDomains
Content-Security-Policy: default-src 'self'; script-src 'self'; [extend per application needs]
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: geolocation=(), microphone=(), camera=()
```

## Independent Audit Lane

An independent security audit (penetration test by an external security firm) is required before production launch and under the following trigger conditions. "Independent" means: performed by an entity that did not write the code being reviewed.

| Trigger | Audit scope | Blocking? |
|---------|------------|----------|
| Initial production launch | Full application penetration test; OWASP Top 10 coverage; API security assessment; session and authentication review | Yes — must complete before production traffic |
| Any change to authentication, session management, or user role handling | Targeted re-test of the auth flows and role boundaries | Yes — must complete before merge to main if the change touches Tier 1 surfaces |
| Any new external integration | Targeted re-test of the new trust boundary | Yes — before the integration is enabled in production |
| Any incident where unauthorized access is suspected | Full forensic review and re-test of all affected components | Yes — production is halted until review is complete |
| Annual review | OWASP Top 10 review; dependency audit; access review; review of any SAST exceptions | No — must complete within 60 days of due date |

### Audit Findings Protocol

| Severity | Required action | Deadline |
|----------|----------------|---------|
| Critical | Immediate remediation; production launch or deployment blocked | Before any production traffic |
| High | Remediation required | Within 30 days |
| Medium | Remediation planned | Within 90 days; tracked in project backlog |
| Low | Reviewed and accepted or deferred | Documented decision within 30 days of finding |
