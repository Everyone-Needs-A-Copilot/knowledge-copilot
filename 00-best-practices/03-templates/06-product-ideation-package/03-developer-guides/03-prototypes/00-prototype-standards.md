## Overview

Prototype work for {{PRODUCT_NAME}} proceeds in two phases.

**Phase 1 — Concept Competition**: Multiple concept directions per critical view are explored and presented simultaneously. The goal is to make a design direction decision. Both phases produce real, runnable Next.js views. Phase 1 concepts are scoped in complexity — fewer states, simpler data, a single primary flow — but they are still interactive, clickable code. The product owner reacts to a real experience, not a picture of one.

**Phase 2 — Full Prototype**: A single selected concept per critical view is built to a level of fidelity sufficient for stakeholder sign-off and handoff to implementation. Phase 2 expands the selected concept into a full navigable prototype covering all critical views, states, and scenarios.

The two phases are sequential. No concept enters Phase 2 without stakeholder approval at the Phase 1 presentation.

## Naming Conventions

### CV Numbers

CV numbers are assigned in the design challenge brief and do not change. If the brief lists:
- CV-01: [View Name]
- CV-02: [View Name]
- CV-03: [View Name]

Then directories are named `cv-01-[view-name]`, `cv-02-[view-name]`, `cv-03-[view-name]`. The number prefix is always two digits with a leading zero.

### Concept Naming with Philosophy Descriptors

Each concept within a CV is named for the design philosophy it represents, not for who made it or what it looks like. The name must communicate the APPROACH being tested.

Format: `concept-[letter]-[philosophy-descriptor]`

Where `[philosophy-descriptor]` is a hyphen-separated word or phrase that describes the organizing idea:
- `concept-a-command-center` — positions the user as an operator with full system visibility
- `concept-b-guided-pipeline` — leads the user step by step through a structured flow
- `concept-c-minimal-focus` — eliminates everything not immediately relevant to the current task

Philosophy descriptors must be agreed by the CDO before concept work begins. They should be distinct enough that a stakeholder can articulate the difference between concepts by name alone.

## Concept Phase (Phase 1)

### Acceptable Formats

Every concept phase submission must be an interactive Next.js page served by the local dev server.

| Format | Acceptable | Notes |
|--------|-----------|-------|
| Interactive Next.js page | Yes | Required. Must run via `pnpm dev` at `localhost:3000/prototypes/cv-XX/concept-X` |
| Static screenshots (PNG/JPG) | Documentation only | May accompany the concept for README documentation; not the deliverable |
| Figma frames | No | Not acceptable as a concept deliverable |
| HTML/CSS static mockup | No | Must be a Next.js page, not standalone HTML |
| Wireframe sketch (digital) | No | Not acceptable at any stage |
| Hand-drawn sketch | No | Not acceptable at any stage |

### Required Fidelity

Each concept must demonstrate:

- [ ] The information hierarchy for the critical view (what is primary, secondary, tertiary)
- [ ] The primary action the user takes on this view
- [ ] How the view handles the "loaded with data" state (not just an empty screen)
- [ ] Responsive intent: desktop-first minimum; note if mobile behavior differs significantly

### What Is NOT Required in Phase 1

- Real API calls or live data
- Navigation between views (each CV is self-contained at this phase)
- Error states (unless the CV specifically tests error handling)
- Animation or micro-interactions
- Final copy (use representative placeholder data)
- Accessibility compliance (this is validated in Phase 2)

What IS required: a running Next.js page that renders the view with representative data and responds to user interaction for the primary action.

### Concept README.md Requirements

Every concept must have a `README.md` in its directory with:

```markdown
# CV-[number]: [View Name] — Concept [Letter]: [Philosophy Descriptor]

## Design Hypothesis
What does this concept test? What assumption are we making about user preference or behavior?

## Key Decisions
- [Decision 1 and the reason for it]
- [Decision 2 and the reason for it]

## What to Look For When Reviewing
- [Specific question or observation the reviewer should focus on]

## What This Concept Does NOT Address
- [Known gaps or out-of-scope elements]

## How to View
[Instructions: open the image files, run the local server, open the Figma link, etc.]
```

## Full Prototype Phase (Phase 2)

### Scope

Phase 2 builds ONE selected concept per critical view into a navigable prototype. The selected concept is determined at the Phase 1 presentation.

The full prototype must demonstrate the complete user flow through all critical views in sequence. A user must be able to navigate from the first CV to the last CV without breaking.

### Technical Requirements

| Requirement | Standard |
|-------------|---------|
| Framework | {{STACK}} matching the production stack |
| Styling | Match the production stack |
| Data | Static JSON fixture files — no live API required |
| Navigation | All inter-view navigation must work |
| Responsive | Desktop (1280px+) required; tablet (768px) recommended |
| Error states | At least one error state per view must be demonstrable |
| Loading states | At minimum a skeleton or spinner for async-feeling interactions |
| Accessibility | WCAG 2.1 AA for all interactive elements |
| Browser support | Latest Chrome required; latest Safari and Firefox recommended |

### What is NOT Required in Phase 2

- Live backend or real API calls
- Authentication (a mock user session is acceptable)
- Form validation beyond happy path
- Full mobile responsiveness (unless in-scope per the brief)
- Performance optimization (production optimization is for the build phase)

## Prototype-to-Branch Strategy

Prototype work lives in branches, not on `main`. The following branching convention applies:

### Concept Phase Branches

Each concept gets its own branch:

```
prototype/cv-01-concept-a-[philosophy]
prototype/cv-01-concept-b-[philosophy]
prototype/cv-02-concept-a-[philosophy]
```

Concept branches are created from `main` at the point the concept phase begins. They are never merged to `main` — they exist solely for review and comparison.

### Demo Branch

A `demo` branch is maintained for stakeholder-facing presentations. Before a presentation:

1. The CDO selects which concepts to include in the demo.
2. Selected concept branches are cherry-picked or merged into `demo`.
3. `demo` is deployed to the staging environment.
4. `demo` is never merged back to `main`.

### Feature Branch (Phase 2)

Once a concept is selected for Phase 2, a feature branch is created from `main`:

```
feature/[view-name]-prototype
```

The selected concept code is ported (not merged) into the feature branch and developed to full prototype fidelity. This branch is reviewed and, once approved, can serve as the starting point for production implementation.

## Pre-Presentation Verification Checklist

This checklist is completed by the presenter immediately before the stakeholder presentation. Do not present without completing it.

### Concept Phase Checklist

- [ ] All concept directories exist and follow the naming convention
- [ ] Every concept has a `README.md` with all required sections completed
- [ ] Every concept shows the "loaded with data" state (no empty screens)
- [ ] All static assets load correctly (no broken image paths)
- [ ] The prototype hub links to all concepts and all links resolve
- [ ] The demo branch is deployed and accessible at the staging URL
- [ ] The staging URL has been tested on the device used for the presentation
- [ ] Each concept can be explained in one sentence using its philosophy descriptor
- [ ] The presenter can articulate the specific design hypothesis each concept tests

### Full Prototype Phase Checklist

- [ ] All critical views are present and navigable in sequence
- [ ] Navigation between views works without errors in latest Chrome
- [ ] All loading states are present (no blank screens during state transitions)
- [ ] At least one error state per view is demonstrable
- [ ] No browser console errors during the primary user flow
- [ ] All interactive elements have visible focus states
- [ ] Responsive layout holds at 1280px, 1440px, and 1920px viewports
- [ ] Static fixture data is realistic (names, values, dates look plausible)
- [ ] The demo branch is deployed and accessible at the staging URL
- [ ] The staging URL has been tested on the device used for the presentation
- [ ] A backup (screen recording or PDF export) exists in case of connection failure
